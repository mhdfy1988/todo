# 待办：发布与自动更新学习指南

这是一份适合第一次接触本项目发布流程时阅读的操作版说明。完整的安全约束、历史发布记录和资产核验细节见[《Windows 发布与自动更新 v0.1》](./Windows发布与自动更新-v0.1.md)。

## 1. 先理解发布链路

```text
修改代码 → 更新五处版本事实与 CHANGELOG → 本地门禁
→ 推送 main → 推送 v<版本> 标签 → GitHub Actions 构建
→ 生成安装器、.sig、latest.json → 草稿验证 → 公开 Release
```

本地负责尽早发现代码和文档问题；GitHub Actions 使用受保护的发布私钥构建正式更新资产。私钥不应出现在本机仓库中。

## 2. 发布前准备

确认仓库和远端：

```powershell
git status --short --branch
git remote -v
git log -3 --oneline
```

项目要求以下五处版本事实一致：`package.json`、`package-lock.json` 顶层和根包、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 根包。

```powershell
npm.cmd version 0.1.7 --no-git-tag-version
```

然后同步 Tauri 和 Cargo 版本。正式修复必须提升版本号，不能覆盖已经公开的版本。

发布前把内容从 `Unreleased` 收口到正式版本段，并保留空的 `Unreleased`。只使用 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Security`。

## 3. 本地门禁顺序

```powershell
npm.cmd run release:version:check
npm.cmd run release:changelog:check
npm.cmd run desktop:check
npm.cmd run ledger:smoke
npm.cmd run desktop:smoke
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D warnings
npm.cmd run desktop:build
```

版本和 CHANGELOG 检查、前端/Rust 测试、两个 smoke、格式、Clippy 都通过且 release EXE 成功生成，才进入发布。候选安装包只用于手感测试，不能作为正式 Release 资产：

```powershell
npx.cmd tauri build --bundles nsis --ci --no-sign --config src-tauri\tauri.candidate.conf.json
```

## 4. 提交和触发发布

```powershell
git add <本次修改文件>
git diff --cached --check
git commit -m "release: prepare v0.1.7"
git push origin main
git tag v0.1.7
git push origin v0.1.7
```

标签推送会触发 `.github/workflows/release.yml`。不要在标签推送后重复手动触发同一次发布，避免并行创建两个 Release 流程。

## 5. GitHub Actions 做什么

工作流会依次校验版本和 CHANGELOG、拒绝覆盖同版本 Release、重跑测试/格式/Clippy、构建 Windows x64 NSIS、生成 `.sig` 和 `latest.json`，再使用客户端内嵌公钥验签并核对下载地址、平台、版本和哈希。最后回读草稿正文，与 CHANGELOG 当前版本段逐字核对，全部通过后才公开 Release。

失败时：代码或文档检查失败就修复后重跑；构建或验签失败不要手动上传未验证资产；已公开版本必须提升版本号，未公开草稿才允许同版本重试。

## 6. 发布后核对

```powershell
gh run view <run-id> --repo mhdfy1988/todo
gh release view v0.1.7 --repo mhdfy1988/todo
```

Release 必须是非草稿、非预发布，并同时包含 `latest.json`、Windows x64 `setup.exe` 和对应 `.sig`。还要确认 Release 正文与 CHANGELOG 一致，`latest.json` 的下载地址和签名字段正确，并按地址重新下载验证哈希和签名。

## 7. 用户端更新验证

正式 Release 发布后，再在真实安装环境验证：旧版本发现新版本 → 用户确认安装 → 下载验签 → 安装重启 → 任务数据、完成历史、窗口状态和托盘行为保留。这个实机闭环不能由本地 build 或 smoke 代替。

## 8. 常见坑

| 现象 | 处理 |
|---|---|
| PowerShell 拦截 npm | 使用 `npm.cmd` / `npx.cmd` |
| 版本或标签不一致 | 先修五处版本事实，再重跑检查 |
| CHANGELOG 检查失败 | 收口 `Unreleased`，使用标准分类和 ISO 日期 |
| Release 已存在 | 提升版本号，不覆盖已公开产物 |
| 安装器触发 SmartScreen | 当前未配置 Authenticode；先核对 updater `.sig` 和哈希 |
| 重复启动出现两个窗口 | 退出旧构建，只启动一个正式实例；smoke 与 normal 保持隔离 |
